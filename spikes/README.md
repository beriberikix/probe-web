## Bug-fix pass (2026-09-17)

Addressed the known bugs and issues from Phases 0–2 before Phase 3. Fork changes are in `probe-rs` (branch `webusb/nusb-0.2.7`), uncommitted.

- **Fork ROM-table hang: FIXED.** Root cause: `architecture/arm/memory/romtable.rs` implemented `Stream for RomTableIterator` by hand; `poll_next` polled the `read_32` future once and dropped it on `Pending`, abandoning the USB transfer (nothing woke the task; the J-Link was left mid-command and re-enumerated). Replaced with a plain async loop. Native `examples/e2e_romtable.rs` now parses AP0's ROM table in ~2 s. Over WebUSB: flasher `?op=info` → 1 DP, 7 APs, 26 component nodes in 10.5 s (`INFO_RESULT=PASS`); the inspect app shows the tree.
- **Fork auto-detect hang: FIXED (same bug), plus two bugs it had been hiding.** With the hang gone, auto-detect on the nRF9160 picked `RP235x` (the fork's registry matches any Arm-designed Cortex-M33 ROM table, part 0x4c9, to it) and then panicked on an ADIv6 AP address against an ADIv5 DP (`unreachable!` in `select_ap_and_ap_bank`). Fixes: that `unreachable!` returns `ArmError::WrongApVersion`; the generic registry lookup no longer guesses a target from an Arm-designed ROM table; master's RP235x chip-ID detection hook is ported (`vendor/raspberrypi`, detection only); `try_detect_arm_chip` closes the interface before propagating errors; RISC-V/Xtensa detection checks for the interface first and logs instead of failing detection (as master). Native `examples/e2e_autodetect.rs` on the nRF9160: clean "unable to load specification for chip" in 139 ms (master cannot auto-detect it either: its first ROM table is Arm's). MCXA153 (MCU-Link CMSIS-DAP): native auto-detect no longer hangs and fails cleanly in 64 ms (its ROM table reports NXP with PART 0, which cannot identify a chip, so no `part:` was added to the YAML); native ROM-table parse works.
- **Fork wasm hazards: FIXED.** 48 `thread::sleep` → `usb_util::wait(..).await` (all were in async fns), 7 `std::time::Instant` imports → `web_time`. `clippy.toml` now bans `std::thread::sleep`, `Instant::now`, `SystemTime::now` and the std `Instant` type; the ban is enforced for wasm32 (`cargo clippy -p probe-rs --target wasm32-unknown-unknown --no-default-features --features builtin-targets`, with `--cfg=web_sys_unstable_apis`) and allowed natively, where `web_time::Instant` is the std type. Clean, and a planted violation is caught.
- **Timeouts as control flow (WebUSB cannot cancel a transfer):** ESP USB-JTAG no longer drains by reading until a timeout on wasm (resynchronises with clocked bits instead) and its descriptor retry waits between attempts; J-Link `read` gives up after repeated zero-length reads; USB timeouts on wasm say the probe must be reopened. ST-Link (no USB reset-and-retry on wasm) and WCH-Link (1 s per-command timeout on wasm) changes are **hardware-unverified**. SWO readers still use timeouts; probe-web has no SWO feature (known limitation).
- **`FakeProbe`:** DP/AP register access and `flush` return `NotImplemented`/`Ok` instead of `todo!()`, so the worker's fake scan runs (5 events) instead of panicking.
- **Worker crash no longer hangs the page.** The worker posts `fatal:<reason>` from a panic hook, when its server stops, and from `error`/`unhandledrejection`/failed start in `local-worker.js`. The transport closes on `fatal:`, `onerror` or `onmessageerror` (pending calls fail), accepts only the exact `ready`, and times out start-up (30 s) and the schema handshake (15 s). The SDK reports such failures as `kind: 'worker-crashed'` with the reason (`Client.crashReason`).
