# Phase 0 spikes

Each spike has a literal exit criterion; "compiles" is not a result.

| Spike | Question | Result |
|---|---|---|
| A `rpc-ws` | Can `probe-rs-rpc-client` compiled to wasm32 talk to a native `probe-rs serve` over the browser WebSocket API? | **PASS** 2026-09-15. Chrome → `ws://127.0.0.1:3000/worker`, subprotocol `probe-rs.challenge-frame`, sha512 challenge handshake, `GetAllSchemas` compatible, `chips/list` = 266 families, 1055 ms end to end. Needs the patch in `../../prs-wasm-rpc` (worktree `wasm-rpc-client`, 6 files, +104/-31): tokio feature gating in `probe-rs-rpc`/`probe-rs-rpc-client`, wasm `WireSpawn`, timeout shim, byte-based uploads, and `serve.rs` sending the challenge as the first frame when the client offers the subprotocol. |
| B `webusb-worker` | Can the fork's async probe-rs + nusb WebUSB run inside a Web Worker, with postcard frames over `postMessage`? | **PASS** 2026-09-15 on FRDM-MCXA153 (MCU-Link CMSIS-DAP v2, SWD). Worker up in 32 ms, unmodified `probe-rs-rpc-client` over `postMessage`, schema check passed, `chips/list` = 204 families (fork), `probe/list` = 1, attach 36 ms, halt at pc=0x898, `memory/read32` @0x0 = [20006000, 00000e51, 000001e5, 00000dd3], resume; 599 ms end to end. Verified out-of-band: after navigating the tab away, native `probe-rs read --chip MCXA153 --protocol swd b32 0x0 4` returned the identical `20006000 00000e51 000001e5 00000dd3`. Finding: the worker's schema report advertises `master`'s full `ENDPOINT_LIST` although only 6 endpoints are dispatched, so `ensure_compatible` passes vacuously; `probe-web-local` must publish a truthful endpoint list (capability negotiation). |
| C `schema-ts` | Can the SDK's TypeScript types be generated from the RPC schema and match what crosses the wasm boundary? | **PASS** 2026-09-15. Instead of `tsify` on upstream types (orphan rule), `schema-ts` walks `probe-rs-rpc`'s postcard-schema model: 160 types, 66 endpoints, 5 topics → `probe-rs-rpc.d.ts` (1067 lines). A Node round-trip of `AttachRequest`/`AttachResult`/u64 through `serde-wasm-bindgen` is identical to the generated shapes under this contract: externally tagged enums, u64 as `bigint` (`serialize_large_number_types_as_bigints`), None/unit as `null` (`serialize_missing_as_null`), `Vec<u8>` as `Array<number>`. Byte-heavy endpoints (RTT, flash regions, temp-file append) will want a `Uint8Array` fast path in the SDK. |
| D perf | Is WebUSB throughput a problem, and would keep-alive endpoints help? | **PASS, question dissolved** 2026-09-15 on FRDM-MCXA153. Instrumented `usb_util` (fork, `stats` module) for a 4 KiB flash+verify: 2112 writes + 2112 reads, 54 342 bytes, **1.15 s in the browser (release wasm; 1.21 s debug) vs 0.99 s native**. Per transfer: submit→complete 225 µs, endpoint creation 1–3 µs. The 16 s figure from the earlier session was an artifact of per-transfer console tracing that was later stripped; endpoint keep-alive is not worth doing. Remaining ~15 % gap is Chrome's per-transfer round trip; the real lever, if ever needed, is fewer transfers (CMSIS-DAP block transfers), not the USB layer. Verified out-of-band: tag `SPIKE-D-REL-2133` written from the browser was read back natively at 0x1F000 after the tab released the device (`probe-rs read --chip MCXA153 --protocol swd b8 0x1F000 32`). |
| E `defmt-wasm` | Does `defmt-decoder` decode an RTT stream from ELF bytes in wasm, identical to native? | **PASS** 2026-09-15. Fixture: `defmt-fixture/` (thumbv7m, `defmt-semihosting`, run under `qemu-system-arm` lm3s6965evb → 56-byte stream, 5 frames incl. `{:?}` struct, `{:#x}` u64, f32, str, negative ints). `defmt-wasm/run.sh` decodes natively and in wasm (Node); outputs byte-identical, wasm decode 9.4 ms. `defmt-decoder` 1.1 compiles for wasm32 unchanged. |

Run A: `cd rpc-ws && ./build.sh`, start `probe-rs serve` from `rpc-ws/serve/` (config there: user `spike`, token `spike`), serve `www/` with `../serve_nocache.py` (port 8798), open `http://127.0.0.1:8798/?auto=1`.
